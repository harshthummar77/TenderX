# TenderBridge — Data dictionary

25 Prisma models → 26 tables (the 26th is the implicit `_CategoryToVendor` join table).
Source of truth: `server/prisma/schema/*.prisma`. Relationships: [`er-diagram.md`](er-diagram.md).

## Conventions that apply to every table

| Rule | Detail |
|---|---|
| Primary key | `uuid(7)` in a `uuid` column — time-sortable, index-friendly, non-enumerable. Generated by Prisma, **not** by a database default, so raw-SQL inserts must supply one. |
| Money | `numeric(18,2)`. `decimal.js` in services, fixed-2 **string** over the wire. Never a JS `number`. |
| Quantity | `numeric(18,3)` — supports 0.5 kg, 2.25 m. |
| Percentages | `numeric(5,2)`; evaluation scores `numeric(6,2)`; vendor rating `numeric(3,2)`. |
| Timestamps | `timestamptz(3)`, always UTC. Display timezone is a client concern. |
| Names | Tables `snake_case` plural via `@@map`. **Columns stay `camelCase`** — the models carry no per-field `@map`, so every raw-SQL reference must double-quote them. |
| Deletion | Nothing is hard-deleted. `CANCELLED` / `WITHDRAWN` / `BLACKLISTED` statuses replace it. |
| Derived columns | `PurchaseOrderItem.received/accepted/invoicedQuantity`, `Invoice.amountPaid`, `Grn.status`, `PurchaseOrder.fulfilmentStatus` are maintained by services inside transactions. No user sets them. |

## Identity — `identity.prisma`

### `users`
Every human login. A user belongs to **exactly one party**: `organizationId` XOR `vendorId`; a
`PLATFORM_ADMIN` has neither. Enforced by the `user_single_party` CHECK.

| Column | Notes |
|---|---|
| `email` | Unique, always written lowercase (citext was cut — see `00 §3`). |
| `passwordHash` | bcryptjs, cost 12. |
| `role` | `PLATFORM_ADMIN` / `ORG_ADMIN` / `ORG_OFFICER` / `VENDOR`. Drives the whole permission map (plan 04). |
| `status` | `INVITED` until the invitation is accepted. |
| `failedLoginCount`, `lockedUntil` | Lockout after repeated failures (plan 03). |
| `resetTokenHash`, `resetTokenExpiresAt` | Password reset. The raw token is never stored. |

### `refresh_tokens`
One row per issued refresh token. Rotation: each use issues a new row and revokes the old one.

| Column | Notes |
|---|---|
| `tokenHash` | SHA-256 of the opaque token. A stolen dump yields no usable tokens. |
| `familyId` | Rotation family. Re-use of an already-rotated token revokes the **whole family** — the standard refresh-token-reuse detection. |
| `replacedById` | The row that superseded this one. |

### `invitations`
Pending invitations for officers and vendor staff. `tokenHash` is hashed like a refresh token;
`acceptedAt` / `revokedAt` close the row instead of deleting it.

### `organizations`
Buyer tenants. `stateCode` is the GST state code (e.g. `24`) and decides CGST+SGST vs IGST on every
document the org issues. `settings` is a JSON column typed by `orgSettingsSchema` in
`@tb/shared` — match tolerance, approval threshold, number prefixes, and defaults. A JSON column
instead of eight more columns is deliberate: these change often and are never queried across rows.

### `vendors`
Supplier companies (not users — a vendor can have several staff logins).

| Column | Notes |
|---|---|
| `status` | `PENDING_APPROVAL → APPROVED / REJECTED`, later `SUSPENDED` / `BLACKLISTED`. Only `APPROVED` vendors can be invited to tenders. |
| `bankAccountNumber`, `bankIfsc` | **Never** appear in a public DTO (plan 06). |
| `rating`, `totalOrders`, `onTimeDeliveryRate` | Performance figures computed in plan 15; they feed the vendor-performance criterion of the scoring engine. |

### `categories`
Flat classification shared by tenders and vendors. Nesting was cut (`00 §3`): a `parentId`
self-relation would put a recursive CTE behind every category query. Linked to vendors through the
implicit `_CategoryToVendor` join table.

## Sourcing — `sourcing.prisma`

### `tenders`
The RFQ. `status` covers the **sourcing lifecycle only** — it never says anything about POs,
invoices or payments (defect C2).

| Column | Notes |
|---|---|
| `referenceNumber` | `TND/2025-26/000012`, unique per organization, from `number_sequences`. |
| `estimatedBudget` | Internal only — never serialised to a vendor. |
| `bidSubmissionDeadline` | **The seal breaks here.** Before it, no buyer can read bid amounts. |
| `bidOpenedAt` | Set once, when the seal is broken. |
| `evaluationMethod`, `criteria` | `LOWEST_PRICE` or `WEIGHTED_SCORE` with a JSON criteria array: `[{ key, label, weight, direction }]` (plan 09). |
| `recommended*` / `awarded*` | Recommendation and award are separate acts by separate people — that is the separation of duties (defect C6). |
| `@@index([status, bidSubmissionDeadline])` | Drives the deadline sweeper and lazy-close-on-read. |

### `tender_items`
The itemised RFQ. `srNo` is unique per tender. `taxRatePercent` defaults to 18. Start of the
six-hop chain.

### `tender_invitations`
Which vendors were invited, and whether they viewed or declined. Unique per `(tender, vendor)`.

### `quotations`
A vendor bid. Sealed: amounts are unreadable to the buyer until the deadline passes.

| Column | Notes |
|---|---|
| `sealHash` | SHA-256 of the canonical submitted payload — proof the bid was not altered after submission. |
| `revisionNumber`, `revisionOfId`, `isLatest` | Revisions before the deadline. The `one_latest_quotation` partial unique index guarantees exactly one current revision per vendor per tender. |
| `priceScore`, `technicalScore`, `totalScore`, `rank` | Written by the scoring engine (plan 09). |
| `criteriaScores` | Manual per-criterion scores, JSON. |

### `quotation_items`
Per-line pricing against a `tenderItemId`. Without this, bid comparison is meaningless (defect C1).

### `approvals`
One row per approval request — award, invoice or payment. `requestedById` can never equal
`decidedById`. The `one_pending_approval` partial unique index blocks a double-submission race.

## Procurement — `procurement.prisma`

### `purchase_orders`
Issued against an awarded quotation. Everything downstream is one-to-many (defect C7).

| Column | Notes |
|---|---|
| `poNumber` | `PO/2025-26/000042`, unique per organization, gapless, fiscal-year scoped. |
| `status` / `fulfilmentStatus` | Two axes: the PO lifecycle, and the **derived** fulfilment state. |
| `buyer*` / `vendor*` snapshot | Name, GSTIN, address and state code frozen at issue. An issued PO is a legal document; a later vendor address change must not alter it. |
| `placeOfSupplyStateCode`, `taxRegime` | `INTRA_STATE` → CGST+SGST, `INTER_STATE` → IGST (plan 10). |
| `cgst/sgst/igstAmount`, `roundOff` | Full GST breakdown, per document and per line (defect C4). |
| `one_active_po_per_quotation` | Partial unique index: one live PO per quotation; cancelling frees it for re-award. |

### `purchase_order_items`
Ordered lines with their own tax split. The three derived running totals — `receivedQuantity`,
`acceptedQuantity`, `invoicedQuantity` — are only ever written inside a transaction holding a
`SELECT … FOR UPDATE` row lock (defect C8). `po_item_positive` enforces `quantity > 0` and
`unitPrice >= 0`.

### `deliveries` / `delivery_items`
A dispatch note from the vendor. Many per PO — partial shipments are normal.

### `grns` / `grn_items`
Goods received note, raised by the buyer. `grns.status` is **derived** from its items
(`ACCEPTED` / `PARTIALLY_ACCEPTED` / `REJECTED`). `grn_quantity_reconciles` enforces
`acceptedQuantity + rejectedQuantity = receivedQuantity` at the database level.

### `invoices`
**Raised by the vendor**, verified by the buyer (defect C3) — never generated from the PO.

| Column | Notes |
|---|---|
| `vendorInvoiceNumber` | The number on the vendor document. Unique per vendor: duplicate-invoice detection. |
| `referenceNumber` | Our internal `INV/2025-26/000018`. |
| `matchStatus`, `matchResult`, `matchRunAt` | The three-way match: `NOT_RUN → MATCHED / EXCEPTION`, with the full check list stored as JSON (plan 12). |
| `overriddenById`, `overrideReason` | An exception can be overridden, but never silently — the override is attributed and reasoned. |
| `amountPaid` | Derived: the sum of payment **gross** amounts. `invoice_not_overpaid` caps it at `totalAmount`. |

### `invoice_items`
Billed lines, each tied to a `purchaseOrderItemId` — the last hop of the chain.

### `payments`
Many payments per invoice (part payments).

> **The TDS insight, stated once.** `grossAmount` is what reduces the invoice balance.
> `netAmount = grossAmount − tdsAmount − retentionAmount − otherDeduction` is only what left the
> bank. Settlement compares `amountPaid` (sum of **gross**) to `totalAmount`. Getting this backwards
> means invoices never settle (plan 13).

`tdsSection` records the section the deduction was made under (`194C`, `194J`).
`referenceNumber` is the UTR or cheque number.

## Platform — `platform.prisma`

### `documents`
Registry of every uploaded file. The bytes live in Cloudinary (private); `storageKey` is the
Cloudinary `public_id` and downloads are served through signed, expiring URLs (defect C11).
`ownerType` + `ownerId` is a loose polymorphic pointer, indexed together; `checksum` is the SHA-256
of the bytes.

### `notifications`
Written **in the same transaction** as the state change it announces, so it cannot be lost if SMTP
is down. `emailSentAt` / `emailError` record the best-effort send, which is never awaited on the
critical path (defect C12).

### `activity_logs`
The audit log. Append-only and hash-chained.

| Column | Notes |
|---|---|
| `sequence` | `bigserial`, unique — the chain order. |
| `hash`, `previousHash` | `sha256(canonical(row) + previousHash)`. Any edit to history breaks every later link, and the verify endpoint (plan 14) reports where. |
| `before`, `after` | JSON snapshots of the change. |
| `severity` | `INFO` / `NOTABLE` / `SECURITY`. |

Two Postgres rules make it genuinely append-only, so the application itself cannot rewrite history
(defect C9):

```sql
CREATE RULE activity_logs_no_update AS ON UPDATE TO activity_logs DO INSTEAD NOTHING;
CREATE RULE activity_logs_no_delete AS ON DELETE TO activity_logs DO INSTEAD NOTHING;
```

Demonstrate it live: `UPDATE activity_logs SET summary = 'nothing happened' WHERE id = '…';`
answers `UPDATE 0`.

### `number_sequences`
One row per `(organization, docType, fiscalYear)`. An atomic
`INSERT … ON CONFLICT DO UPDATE … RETURNING` hands out the next value, which is why two officers
clicking "Generate PO" at the same moment cannot produce two POs with the same number (defect C15).
`padding` controls the zero-fill: `PO/2025-26/000042`.

## Constraints that live only in SQL

Migration `20260913102500_constraints`. Prisma cannot express any of these, so that file is their
source of truth. Column names are double-quoted because columns are `camelCase`.

| Object | Table | Guarantee |
|---|---|---|
| `user_single_party` (CHECK) | `users` | At most one of `organizationId`, `vendorId` is set. |
| `grn_quantity_reconciles` (CHECK) | `grn_items` | `accepted + rejected = received`. |
| `invoice_not_overpaid` (CHECK) | `invoices` | `amountPaid <= totalAmount`. |
| `po_item_positive` (CHECK) | `purchase_order_items` | `quantity > 0` and `unitPrice >= 0`. |
| `one_active_po_per_quotation` (partial unique) | `purchase_orders` | One live PO per quotation; `CANCELLED` is excluded. |
| `one_latest_quotation` (partial unique) | `quotations` | One current revision per `(tender, vendor)`. |
| `one_pending_approval` (partial unique) | `approvals` | One open approval per entity. |
| `activity_logs_no_update` / `_no_delete` (RULE) | `activity_logs` | UPDATE and DELETE silently affect 0 rows. |

No extensions are required — `citext` and `pg_trgm` were cut (`00 §3`). Everything above is standard
Postgres and runs unchanged on Neon.
